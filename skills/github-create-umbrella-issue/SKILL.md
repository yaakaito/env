# umbrella issue を作成する

会話で議論したタスクを umbrella issue にまとめる。
umbrella issue と子 issue は、それぞれ単体で読めば、この会話に参加していない人でも作業を始められる状態にする。
会話を読まないと分からない前提を残さず、作業に必要なコードやドキュメント、関連 issue や PR、制約を本文に含める。

## 既存の issue を確かめる

議論の途中で繰り返し実行されるため、作成前に同等の umbrella issue を探す。
この会話で作成した issue を最優先の候補とし、なければ対象 repository の open issue を検索する。
候補があれば、ベースにしてよいかをユーザーに確認する。
どの候補を使うかを推測で決めない。

## 内容を固める

会話と引数から本文を組み立てる。
作業を始められる状態にするための情報が足りない場合は、不足点を挙げて質問する。
論点の深掘りが必要なら `/dig` を提案する。

子 issue を作るかどうかは、実行のたびにユーザーに確認する。
作る場合は sub-issue として紐付ける。
既存の issue も sub-issue として取り込める。

## 議論の経緯をコメントに残す

本文には現在の結論だけを書き、そこに至った経緯は umbrella issue のコメントに残す。
本文だけを読む人が経緯にたどり着けるよう、本文からログコメントへのリンクを張る。
コメントは要約を基本とし、発言の抜粋は要約だけでは判断の根拠が伝わらない場合に `<details>` で添える。

コメントの先頭に `<!-- umbrella-log -->` を入れる。
2 回目以降の実行では、この目印が付いたコメントを読み、まだ記録していない議論だけを新しいコメントとして追記する。

## 公開する

本文、子 issue、ログコメントの下書きをまとめて提示し、一度の承認を得てから公開する。
既存の issue を更新する場合は、本文の変更点が分かるように示す。
公開後、作成または更新した issue の URL を報告する。
