# Codex Review

Codex CLI の独立したレビュー結果をコードと照合し、実害のある問題を報告する。
レビューのみの依頼ではコードを変更しない。
修正も依頼されている場合は、妥当な指摘の修正と検証まで進め、同じ範囲の再承認を求めない。

## 対象を確定する

ユーザーが指定したコミット、比較元、ファイルの範囲を優先する。
指定がなければ `git status --short` と `git diff HEAD` で、staged と unstaged の変更を確認する。
`git diff HEAD` に含まれない untracked ファイルは、変更に関連するものを確認する。
対象の変更がなければ、その旨を伝えて終了する。

レビュー対象は差分とするが、挙動を判断するために呼び出し元、契約、テストを読むことはできる。
差分と無関係な既存の問題はレビュー対象へ広げない。

## Codex を実行する

利用する CLI の `codex exec --help` を確認し、読み取り専用の sandbox で起動する。
CLI が利用できない場合や実行に失敗した場合は、未実施の範囲と原因を報告し、成功したレビューとして扱わない。

まず変更に必要な観点を選ぶ。
バグ、セキュリティ、パフォーマンス、テスト、アーキテクチャは候補であり、常に五つのプロセスを起動する必要はない。
小さな変更は一つのプロセスで確認し、独立した観点に分けることで見落としを減らせる変更は並列にレビューする。
各プロセスには同じ対象範囲と、担当する観点を渡す。

プロンプトには次を含める。

- 対象リポジトリ、差分を取得するコマンド、関連する untracked ファイル、担当する観点。
- 変更から生じる実害を根拠とともに指摘し、命名の好みやフォーマットの指摘は除く。
- 各指摘に重要度、ファイルと行、問題が起きる条件、影響を含める。未確認事項を断定せず、指摘がなければその旨を報告する。
- ファイルを編集せず、自分でレビューを完了する。この skill や別のレビュー subprocess を再帰的に起動しない。

例えば、組み立てたプロンプトを一時ファイルに保存した場合は次の形で実行できる。
変数には実際の絶対パスを設定し、並列実行ではプロセスごとに異なる出力先を使う。

```bash
codex exec --sandbox read-only -C "$REVIEW_REPO" \
  --output-last-message "$REVIEW_OUTPUT" - < "$REVIEW_PROMPT"
```

実行ログと最終回答を区別し、終了状態と最終回答を確認する。
レビュー中に対象の差分が変わった場合は、結果がどの変更に対するものかを確認してから採用する。
一時ファイルが必要なら `mktemp -d` で専用ディレクトリを作成し、終了後はこの実行で作成したものだけを削除する。

## 結果を検証する

各指摘を実際のコード、契約、テストで検証し、重複と誤検知を除く。
重要度の高い順に、問題が起きる条件と影響、該当箇所を報告する。
指摘なしの場合も、実施した範囲と未確認の範囲を区別する。
実行に失敗したプロセスを「問題なし」に含めない。

修正も依頼されている場合は、検証済みの問題を修正し、挙動に対応するテストやプロジェクトの確認手順を実行する。
修正した問題、残った問題、検証結果を報告して完了する。
レビューのみの依頼では、検証済みの指摘と確認上の限界の報告で完了する。
